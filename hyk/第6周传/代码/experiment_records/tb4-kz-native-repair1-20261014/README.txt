原生 KZ repair1：修复、开发复测与是否扩至 30 题
2026-10-14

结论
本轮值得先做 3 题开发复测，不宜立即把未经验证的修复扩成 30 题。
原生 KZ 不是 kz-dsh；本目录只运行 KZ2.0 原 Python 求解循环。
旧项目、旧结果、DSH 和其他进行中的实验不修改。

确认的故障与修复
1. 三次提交摘要超过 1600 字符导致提前退出：取消摘要额外字符上限，保留类型、
   空值、NUL 检查及公共模型输出限制；不截断摘要。
2. 子目标绝对路径被拒绝、无效计划丢失后重复使用未知 ID：允许解析到工作区内的
   绝对目标路径，保留被拒绝的完整计划及原错误，让下一次普通决策修正。
   不替模型生成目标、不把 echo 当验证、不增加单独的策略声明调用。
3. 简单 bash 包装或 cd 后的同一检查不被识别：保守统一单一字面命令和 cwd，
   不重写实际命令，不合并包含重定向、管道或额外命令的检查。
4. 格式错误次数与两轮 Critic 计数不能自动结束任务：生产配置将这两个终止上限
   设为 sys.maxsize，继续使用同一个 3 小时预算。其他原生角色、冷却、记忆、
   正交机制保持；关闭回溯的历史实验配置保持。本版本明确是工程修复变体。
5. 未提供 token usage 时标记未知，不填成零。四角色及重试均计实际 HTTP。
6. 守护服务死掉时仍有题内 3 小时超时保护；PID 启动时间校验防止误杀复用 PID。
   审计磁盘写入失败也必须执行超时清理。运行状态区分工程故障和模型提交。

没有注入前三题修复方案、官方测试内容或答案。payments 与 mvcc 的具体代码错误
仍由模型解题；工程修复不等同于这些任务会通过。

验收
18 项修复/传输/扩张决策测试、2 项超时测试通过。真实原生循环执行文件检查；
实际本地 HTTP 首次 503 后重试，四角色共 5 次请求，与台账一致；无模型调用。
历史 33 项回归：原版与修复版均 28 通过、同样 5 失败，失败详情完整保留在
audit/offline-comparison.txt。没有删除或放宽这些测试，不能说历史回归全部通过。
其中旧测试仍使用 uses_memory/旧提醒流程，与冻结版本的 memory_review 协议
不一致；历史恢复标签也有不同预期。本次不借此改动记忆算法；真实效益未验证。
在各真实题环境中还要重新跑无凭据的安装/原生循环验收，然后才允许该题付费请求。

预先固定的扩张决定
任务名单沿用原来冻结的 30 题，不按成绩换题。先复测已暴露的 payments、mvcc、uefi。
三题都是开发数据，不能充当新盲测。其余 27 题用于后续评估，分开报告。
扩张条件：三题全部工程完成、无未注册计划遗留、都取得官方评分，且至少一题通过。
这只是投入是否值得的开发门槛，不是统计显著性或算法收益结论。
未达到则停止扩张并记录原因；不自动改代码重试。不与旧结果混池取最好值。
一次任务最多一个付费尝试，最大总数 30；串行；每题 3 小时；原有模型、上下文、
输出、原任务 CPU/内存、官方评分器保持。每题独立容器、工作区、会话和运行期记忆。
原生与 DSH 执行器本来不同，因此这是 Harness 对比，不是同执行器纯算法消融。

写心跳失败退出。原生 KZ 第三题的退出 1 不能仅凭这个根盘故障推断同一个根因。
新包准备放在 /mnt/sdb/home/lizh639/tb4-kz-native-repair1-20261014，旧盘数据不移动。
每次任务准入检查 Docker 盘至少 max(30 GiB, 2×该题声明 storage) 可用，日志盘
至少 2 GiB；不足时保持队列暂停，不启动模型。原容器保留，暂停后由管理员安排
存储，脚本不会全局 prune，不删其他任务容器、镜像、卷或历史实验。

启动
运行 Start-Secure.ps1：先检查源锁、依赖、磁盘和 Docker，再提示输入本次 TaoToken
密钥（隐藏输入，不能在聊天里发送）。密钥只经 SSH stdin 交给新服务进程，不落盘，
不读取旧进程或其他任务密钥。根盘未恢复前此脚本会直接拒绝启动。
服务器启动入口为 campaign.py --launch；调度独立于本机连接。
ready.json 固定源码和运行包。进程异常或已有 launch-once.marker 时禁止自动重放，
需要对已准入任务作显式核对；不因调度重启重复付费。

复核

offline_accept.py 使用 --network none 容器执行；audit/offline.json 区分新检查通过
与历史回归已知失败。pack.py 根据验收结果构建独立安装包和源码清单。
