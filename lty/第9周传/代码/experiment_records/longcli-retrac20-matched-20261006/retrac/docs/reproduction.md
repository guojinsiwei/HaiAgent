# RE-TRAC 复现范围与 LongCLI-Bench 迁移说明

本项目实现论文 **RE-TRAC: REcursive TRAjectory Compression for Deep Search Agents**（arXiv:2602.02486v1，2026-02-02）的训练无关推理框架，并把工具交互迁移到 LongCLI-Bench 的终端环境。本项目不声称复现论文报告的准确率，也不把通用模型套上提示词称为已经复现 RE-TRAC-4B / RE-TRAC-30B-A3B 的训练。

本次交付范围为适配器代码、运行配置、方法说明与离线协议测试，供交接给实际运行者使用。按照用户要求，不在本次工作中运行模型实验或 LongCLI-Bench 正式评测；离线测试通过不能作为基准性能结果。

## 论文算法与代码对应

论文第 4.1 节定义 `S_t = Compress(τ_t, S_{t-1}; C)`。`τ_t` 是本轮完整可见轨迹，`S_{t-1}` 是上一轮结构化状态，`C` 是固定压缩规范。关键在于跨轮递归继承已有证据和未完成分支，不能只截取最新终端输出，也不能把每轮当作互不相关的重试。

1. 第 1 轮从原始任务开始，交替产生行动并观察工具结果，形成 ReAct 轨迹。
2. 当本轮产生最终回答或达到上下文/资源边界时，压缩已有状态和本轮轨迹。
3. 新建下一轮模型消息上下文；保留原始任务，并将上一轮状态连同 continuation prompt 放在开头。不要把各轮原始消息持续拼接回新上下文。
4. 后续轨迹可复用证据、验证存疑信息，也可以推翻摘要中的假设并探索遗漏分支。
5. 默认进行 8 轮。按论文第 4.3 节及 RT@N 定义，选最后一轮的最终回答，不进行多数投票、最高置信度选择或使用真实答案决定提前停止。最后一轮不必再生成不会被后续使用的摘要。

压缩与续跑提示词位于 `src/retrac/prompts.py`。正文提出的三个信息维度，在附录 C.3.1 中具体化为以下结构：

| 版本 | 精确标题 | 对应论文 |
| --- | --- | --- |
| base | `0) Current Answer`；`1) Facts & Evidence Collected`；`2) Analysis & Conclusions`；`3) Source Inventory & Verification Status`；`4) Uncertainties, Limitations, Gaps` | 图 9，小模型及 SFT 模型 |
| full | base 五项，再增加 `5) Failed attempts`；`6) Uncompleted proposals`；`7) Discarded possibilities` | 图 10，较强模型 |

正文并未把结构化状态规定为 JSON。这里按图 9、10 使用带固定标题的纯文本，保留来源、验证状态和证据到结论的关联；额外的终端 JSON 仅用于行动协议。图 11 的续跑指令保留了三个关键点：怀疑摘要、扩大搜索范围、自主重新规划。论文第 5.3 节的 free-use 消融表明，一味相信上一轮摘要会把错误推断和探索范围的限制继续传递。

## 终端任务的必要改动

| 原论文 | 本适配器 |
| --- | --- |
| Web search / visit；工具主要返回检索证据 | 在基准提供的持久终端中输入命令并观察输出 |
| 来源为 URL、页面和实体 | 来源为命令输出、文件路径、测试结果、生成物及已有消息标识 |
| 分支为搜索关键词、候选实体和网页 | 分支为实现方案、排错假设、未完成文件修改与待执行检查 |
| 主要产物为答案文本 | 主要产物可能是环境内的文件和程序行为，由基准在运行后评分 |
| 轮次重建模型上下文 | 只重建消息，不重置容器、工作目录、shell 或已修改文件 |

持久环境是最重要的迁移差异：如果前一轮已经修改文件，后续轮应审查现状，避免机械重放具有副作用的命令。压缩系统提示会保存具体路径、已观察的命令状态、进行中的进程、修改记录和验证结果；这些放在论文已有标题内，不添加另一套声称来自论文的状态格式。

行动协议使用 `analysis`、`commands`、`task_complete`、`final_answer`。每个命令包含 `keystrokes` 和 `duration`；命令在同一终端依次输入。`analysis` 只需简短的操作判断。`task_complete` 是模型结束本轮的信号，不是基准判定成功的真值；该值为 true 时必须让 `commands` 为空，避免尚未读取最后一次执行结果就宣告结束。外部任务评分不能反馈给推理器来筛选轮次。每轮步数上限、整体时间边界、响应解析与上下文预算保留，均属于运行可靠性措施，不能写成论文原设定。其中默认每轮最多 50 次行动响应，是本适配器针对终端任务的预算选择，并非论文的统一轨迹长度。达到预算而未完成全部轮次的运行应单独标记，不能等同完整 RT@8。

## 模型与训练边界

论文第 4.3 节允许 frontier LLM 直接采用该推理流程，无须微调；默认由求解模型自身生成压缩状态（表 6）。使用独立的压缩模型属于论文研究过的变体，实验报告需列出该模型和额外成本。

论文第 4.4 节的小模型结果涉及真实的训练过程：从 Wikipedia 实体树构造约 33K QA；使用 GLM-4.7 收集 4 轮 RE-TRAC 轨迹；过滤后得到约 104K 训练样本；对 Qwen3-4B-Instruct 和 Tongyi-DeepResearch-30B-A3B 做 SFT。此适配器没有重建该数据与训练流程。即便加载作者发布的模型，它仍是面向搜索工具训练的模型，终端协议及 CLI 能力需要独立验证。

## 官方代码对照与复现口径

作者的 [InfoAgent / retrac 仓库](https://github.com/microsoft/InfoAgent/tree/main/retrac) 提供 web search / visit 实现。[默认配置](https://github.com/microsoft/InfoAgent/blob/main/retrac/retrac/deep_research.yaml) 使用 8 轮及 base 压缩提示；[graph.py](https://github.com/microsoft/InfoAgent/blob/main/retrac/retrac/graph.py) 在新轮只注入最近一份摘要，并继续保留原问题。仓库的可变 `main` 分支只作为交叉核对，算法依据固定为用户提供的 v1 论文。

核对时发现一个输出差异：该版官方 `graph.py` 会对最后一轮再次压缩，并在 `final()` 返回末尾摘要；论文第 4.3 节则明确选择最后一轮的答案。本实现遵循论文的答案选择定义，避免把压缩文档误当作求解输出。若要逐行复现某个官方代码版本，需另行固定其提交并明确采用哪一种口径。

## 建议的有效性检查

- 检查第 2 轮及以后是否出现前轮遗留的证据、错误与未完成分支，且没有完整旧轨迹被重新拼接。
- 检查本轮结束后是否真的调用压缩器，而不是将最后回答冒充结构化状态。
- 检查压缩器使用纯文本规范，避免被求解器的 JSON 输出系统提示覆盖。
- 检查轮次间环境是否持续、命令是否真实执行、失败命令是否保留为失败证据。
- 同一模型和任务集比较 1 轮与多轮；统计任务通过率、实际轮数、工具次数、输入输出 token、压缩额外成本、耗时和预算中止率。更高通过率需要真实基准运行证明。
- 将使用替代摘要、输入截断或提前结束的运行单独标记；不可把退化运行悄悄归为论文方法完整执行。
- 保留每轮原始轨迹与结构化状态供离线审计，基准隐藏测试或真实答案不得进入推理输入。
