# v15 多模型职责分离：范围与使用

源版本：`releases/branching-memory-v14`。本次只在新副本修改模型策略适配层及其图搜索入口。
未上传云端、未开启付费请求、未更改旧版本。

## 职责

| 组件 | 输入与职责 | 不允许做什么 |
|---|---|---|
| 行动模型 action | 任务、当前结构化上下文、原规则检索结果；提出初始语义地图和候选命令 | 不整理下一状态，不虚构执行反馈 |
| 证据评估模型 assessment | 已执行动作、真实返回、验证结果、此前上下文；返回原 assessment 字段 | 不写命令、记忆或 next_context，不宣告官方成功 |
| 上下文/记忆模型 memory | 同一份真实观察、动作及此前上下文；返回 next_context 和可选微经验 | 不覆盖 assessment，不直接执行或提交 |
| 原图控制器（代码） | 排序前沿、分支隔离、执行、预算、规则准入和停止门控 | 不新增 LLM 总指挥、辩论循环或成功裁判 |

先生成动作，经真实环境执行，再分别进行证据评估与记忆整理，程序验证并合并为原来的
`TransitionUpdate`。记忆模型不把评估模型的意见当作真实工具反馈；两者直接读取相同的
实际观察。调用串行，避免多个角色同时写工作区。评估格式修复只重试评估，记忆格式修复
只重试记忆；原重试上限不变。没有静默换模型、投票或失败后转单模型兜底。

“多模型”是可独立配置的三个模型角色，不表示必须三个不同厂商或权重。默认沿用原配置，
但客户端、请求、职责提示词和用量统计相互独立。尚无真实性能改进证据。

## 配置

图搜索 CLI `python -m bestfgs ... --engine graph --blocking-memory off` 的原参数照旧。
仅 v15 的该入口默认启用协作；旧的 `RetracPolicyAdapter` 仍保留兼容原接口。
通过 API 使用时，把 `CollaborativePolicyAdapter(config)` 传给原 `TaskRunner`。
Notebook 的 bestfgs/search_only 路由最终调用同一图入口；Raw/evidence 不受影响。
旧的对照/消融协议不是多模型公平性协议，不可把旧计划直接当作新正式实验。

每个角色可设置：

```powershell
$env:BESTFGS_ACTION_MODEL = '你的行动模型名'
$env:BESTFGS_ASSESSMENT_MODEL = '你的证据评估模型名'
$env:BESTFGS_MEMORY_MODEL = '你的上下文模型名'
```

不设置则继承已有 `--provider/--model/--base-url/--api-key-env` 配置。
若更换角色端点或供应商，还必须显式设置对应
`BESTFGS_<ROLE>_BASE_URL`、`BESTFGS_<ROLE>_PROVIDER`（供应商变化时）和
`BESTFGS_<ROLE>_API_KEY_ENV`（值是已有安全环境变量的名字，不是 Key 本身）。
跨供应商还须显式指定角色模型和端点，禁止把原服务密钥自动发到另一端点。
不同角色的温度、请求/格式重试、工具限制等默认沿用原值；本次不调参。

## 保持不变与新增开销

- 图算法、优先级、分支方式、状态合并和已有提交条件未改。
- 微经验的提取字段、证据索引校验、准入、检索、失效策略未改，只换负责生成它的角色。
- 未套入新的 HAI 组件，未改任务清单、模型默认名、工具/交互预算或官方评测。
- 成功率、交互轮次、冗余率定义未改。用量总数现在累加全部角色，并在 `model_usage.roles`
  分角色记录真实 API 请求、响应和 token；不能只计算行动模型来宣称开销下降。
- 原来一次“评估+上下文整理”现在两次请求，所以无重试时每个普通动作周期通常由
  两次模型请求变成三次。每次输出职责较窄，但总时延/token/费用不保证减少。
- 失败分类保留最后调用角色的错误类型，避免把模型格式错误误当网络故障自动重跑。

## 验证

离线测试覆盖职责路由、越权字段拒绝、原成功门控、角色内重试、无静默降级、
记忆关闭模式、真实模拟环境的一步图执行、调用统计和跨端点密钥保护。
这只验证工程接线，不能证明多模型优于单模型；未启动任何新实验。
