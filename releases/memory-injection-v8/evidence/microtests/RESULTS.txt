v8 记忆机制小型验证（2026-10-01）

结论：五类工程行为检查通过四类。所有五类都自动生成了失败记忆，
且在两次相同失败后的下一轮输入中看到了 M1，但 shell 空格改写能绕过拦截。

范围与方法
- 在学院服务器 172.16.108.236 的隔离临时目录运行生产 LiveWorkspace 和 LeanTaskRunner。
- 五类夹具，各做开启记忆/关闭记忆两组，共十次运行。
- 使用真实 Linux 命令和真实返回码；独立夹具断言及成功输出验证目标。
- Actor 决策、修改动作和简短决策说明均是预设脚本，模型 API 调用为 0。
- 这不是 RAW 与 BestFGS 的真实模型对照，也不是正式 benchmark。
- 不能由此证明大模型会主动检索、理解或利用记忆，更不能证明成绩提升。

各类结果
1. 路径不存在：通过。关闭记忆时第三次同命令仍执行失败；开启记忆时
   第三次被拒绝（即使声称 different_route），换为正确路径后验证通过。
   实际失败次数：无记忆 3，有记忆 2。
2. 缺少依赖：通过。第三次不变的失败命令被拒绝；添加本地夹具模块后，
   携带 justified_retry 和 new_evidence 的同命令复测被允许且通过。
   实际失败次数：无记忆 3，有记忆 2。
   边界：此例未自动跟踪新模块依赖，由明确的合理复测声明放行，
   不能声称系统已经自动识别所有导入依赖变化。
3. 矩阵维度错误：通过。拒绝不变重试；修正输入 case.json 后，
   旧记忆被标记 changed_or_unknown_recheck_required，同命令复测通过。
   实际失败次数：无记忆 3，有记忆 2。
4. shell 命令增加空格：未通过。第三次改写命令仍被执行，得到相同错误。
   两组实际失败次数均为 3，开启记忆没有减少这个无效重试。
   后续预设源码修复使夹具目标最终通过，但不掩盖拦截检查失败。
5. 源码修正后复测：通过。修改 rule.py 后，旧记忆被标记需重新检查；
   同一个验证命令没有被错误禁用，并验证通过。两组实际失败次数均为 2。

漏洞定位
lean_memory.py 的 action_key 对 argv/cwd/stdin 的原始 JSON 做哈希。
bash -lc 的命令字符串仅添加无意义空格，哈希就不同。
自动失败记忆的 operation 字段为空，当前可靠匹配也未兜底识别这种等价命令。
因此本例在输入里有 M1、也按格式填写了 review，却仍可重复失败动作。
下一步应做保守的命令等价性识别；不能随便删除 shell 引号内部的空格、
参数或重定向，否则会把真正不同的动作误判为重复。此次只测试，未改算法。

其他校验
- 本地重新运行 81 项单元/回归测试：67 通过，14 因 Linux 执行条件跳过。
- 原实验源码哈希未变，v8 候选源码哈希与封存清单一致。
- 没有修改当前实验、HAI、桌面代码阅读包，也没有替换生产部署。
