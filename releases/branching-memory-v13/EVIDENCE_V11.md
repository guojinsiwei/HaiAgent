# v11：顺序执行、任务内证据、按需回退

本目录是独立开发版本。旧 v10、云端冻结代码、题单和已有结果不改写。v11 **尚不能声称超过 Raw**；离线回归只证明执行契约和修复点，不证明任务成功率。

## 这次改变了什么

默认入口改为 `--engine evidence`。模型沿一个工作区顺序解题，自主决定命令、验证与提交，不再每轮强制调用独立的规划、状态压缩、成功评分模型。完整的命令及返回结果历史保留；工具自身的输出截断仍存在，并不代表无限上下文。

经验限定在**当前任务、当前尝试**：记录实际观察及其文件条件。成功的纯读取，只有命令及依赖条件确实匹配时才能复用；失败记录只是条件化提醒，不因一次失败永久封禁一种做法。缓存返回明确标注来源，不冒充新执行或新测试。为保持读写顺序，只能拦截一个批次开头连续的可复用读取。

当前实现是“可核对的证据台账”，不是自动学会因果规律。它按实际失败/检查义务与时效优先呈现记录，不宣称做了语义相似检索。可缓存读取包括限定参数的 `cat/head/tail/rg` 及 AST 白名单内的 Python `Path(...).read_text/read_bytes`、编码和切片；任意脚本、动态路径、写操作和未知依赖均不自动复用。`rg` 的无匹配非零返回也会保留，缓存遇到非零返回同样停止本批后续命令。

探索从强制扩展树改为模型按需回退：可以恢复一个已保存的文件快照，再尝试其他方案。恢复也消耗一次决策预算；只恢复任务文件，不恢复外部服务、已安装的软件、网络副作用或进程状态。它是一次算法路线调整，不能再把新版简单描述成“原 BestFGS 参数优化”。

模型用 `done=true` 选择当前工作区提交。提交、局部验证通过、官方成功是三个不同字段。交付检查保证导出的补丁能够从指定基础版本重建，不用模型裁判把局部测试判定成任务成功，也不替模型多做免费的最终修复。任务预算结束仍保留可交付草稿及轨迹，不能把草稿算成成功。

验证前后比较新增、删除、改写及权限/链接变化；新建源码不能伪装成“验证通过”。正常缓存和覆盖率输出允许生成，其他临时产物放 `.bestfgs_verify_outputs/`。未执行的后续检查保留为未知；后来一个不同的窄测试通过，不能抹去先前失败。

Git 交付只包含“基础提交 + 导出补丁”，不带候选工作区里的忽略文件。`working_snapshot_validation_passed` 记录工作区检查；最终重建后不免费补跑测试，故 `local_validation_passed=false`、`delivered_validation_status=not_run`，不得把前者当成重建交付物已通过。`roundtrip_verified=true` 仅证明补丁可以应用并精确复现 Git 树，最终正确性仍交给官方评测。

旧路径保留为 `--engine legacy`，仅用于复现/诊断；`--experience-mode legacy` 不属于 evidence 引擎。

## 公平对照和消融

Raw 与新版共用同一个顺序执行器、工具限制、模型 API、普通历史、提交和交付逻辑。Raw 关闭证据记忆与文件快照回退。普通对话历史仍保留：这才是有正常上下文的裸模型基线，而不是人为失忆的弱基线。

`run_comparison.py` 仍使用 `bestfgs`、`raw` 作为输出目录标签，但协议明确记录实际算法；标签本身不表示运行的是旧树搜索。协议同时冻结题单、基础工作区、解释器和依赖指纹、代码哈希、模型参数、任务顺序以及预算。

`run_experience_ablation.py` 默认生成四组小规模开发消融（1–10 题，每题四组）：

| 组别 | 任务内证据 | 文件快照回退 | 用途 |
| --- | --- | --- | --- |
| `raw` | 关闭 | 关闭 | 共用执行器的裸模型 |
| `search_no_memory` | 关闭 | 开启 | 单独检查回退是否值得 |
| `evidence_no_branch` | 开启 | 关闭 | 单独检查证据利用是否值得 |
| `conditioned` | 开启 | 开启 | 完整新版 |

这是一个两因素设计；小样本单次运行的差异只能用于开发决策，不能直接当成统计显著的提升。所有组用相同题目，失败不能临时换题，也不因一组失败而偷偷多试。

历史 v5/v10 Raw 结果不能直接充当 v11 的严格配对基线。普通原始命令行交互、命令批大小、轮次预算含义或基础设施变了，就需要新配对结果。旧结果可作背景参考，不能混在同一个提升百分比里。加载 v11 结果时要求 `runtime_version=evidence-cli-v11`、经验开关、回退开关和决策轮数匹配；缺失则报告数据错误。

## 预算与三个主指标

- **成功率**：官方评测 resolved / 预先冻结的任务数。提交成功与本地验证通过都不能代替官方评测；评测基础设施出错保留为未知，不能静默剔除。
- **交互轮次**：实际执行命令并返回工具反馈的批次数。空提交、仅缓存复用、仅恢复快照不算工具交互；另报 `decision_turns`、逻辑模型调用数、实际 API 请求数和 token，防止把隐藏的推理开销当成效率提升。
- **工具调用冗余率**：沿用 v10 的“条件未变、证据可复用、没有新验证义务”的操作化定义。未知调用保留在分母，并同时报告识别覆盖率/未知范围。重复命令不自动等于冗余，缓存命中也不能直接声称因果上节省了多少工具调用。

v11 `--max-iterations` 是**决策轮数上限**，包含提交、缓存复用和恢复快照。每个决策中的格式修复会额外调用模型，按共用上限重试并独立计入调用数，不伪装成工具轮次。`--max-tool-calls` 是实际执行的任务命令总上限，验证命令也计入。两组不宣称 token 预算相等，实际费用必须看完整 API 用量和缺报情况。

原三个主指标不偷换口径；未知冗余仍不能当成已证明不冗余。补充报告 `cached_tool_observations`、`snapshot_restores`、真实渲染的经验条目数及模型费用，用于判断新机制到底有没有被使用。它们是诊断，不替代官方成功率。

## 本地回归与运行边界

`python validate_v11.py` 运行完整离线回归并生成 `VALIDATION_V11.json`，在本进程内阻止非回环网络请求；模型回复使用假响应，少数网络测试只连接本地假 API 服务。该收据不表示已经进行任何付费模型实验，也不表示在云端 Linux 做过验证。

2026-09-23 的 Windows 完整回归：**582 项，571 通过、11 跳过、0 失败/错误**。跳过项为 Linux 专属进程/准备测试、符号链接权限、POSIX 执行位及缺少 `cat`；Python 读取复用已有在本机真实执行的替代测试。包含真实临时 Git 仓库、子进程执行、默认 CLI 到 notebook 导出、缓存读写顺序、预算和交付一致性的离线端到端用例。上线前仍须在 Linux 隔离环境补跑平台项；不要将这份回归收据当作真实模型成功率。

`evidence-trace.json` 保留决策、真实反馈与缓存来源；`search_checkpoint.json` 原子保存最近可交付草稿；`evidence-result.json` 保存最终结果。预算或中断时若当前为空，可以明确标注后退到最近非空草稿；模型明确提交空补丁则记录空提交，不偷偷换另一个答案。

执行器会从子命令环境中移除控制器的 API Key，并将已知旧快照路径映射到当前工作副本。但复制目录不等于操作系统沙箱：不能保证隔离所有外部路径、进程、网络副作用。实际基准仍应放在隔离容器中。不要把本版本直接覆盖正在运行的云端冻结目录。

## 先生成计划，不开始付费运行

在本版本目录中，使用已准备好的小题单。以下占位路径需替换为真实路径：

```text
python run_experience_ablation.py --task-manifest <prepared-small-manifest.json> --output-root <new-v11-ablation-directory> --python <agent-python> --model deepseek-flash --dry-run
```

默认不调用模型、不创建实验输出、不开始官方评测。检查计划中的四组、模型、预算、题目和哈希后，另行明确加 `--execute` 才会运行；可带 `--expected-protocol-sha256 <reviewed-hash>` 防止检查到执行之间变更。密钥只从启动环境读取，不能写入命令参数或结果文件。

已有准备批次的正式两组计划：

```text
python run_comparison.py plan --plan <frozen-public-plan.json> --prepared-root <prepared-batch-directory> --output-root <new-v11-paired-directory> --model deepseek-flash
```

两容器的现有分片机制仍可用：同一协议、不同 `--shard-index`，每道题的两个方法在同一个分片连续执行，输出和锁避免重复启动。`plan` 不启动任务；正式 `run`、云端守护以及官方评测需要单独确认和部署，本文不表示已经启动。

建议先看小样本四组能否实际触发“读取复用、失败提醒、必要时回退”，并核查正确率和开销；若没有触发或反而变差，应据此收缩机制，不再只凭“提取了多少条经验”判断有效。
