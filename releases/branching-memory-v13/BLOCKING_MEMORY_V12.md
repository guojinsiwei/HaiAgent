# v12：任务内阻塞记忆

本目录是独立开发版本；旧 v11、云端冻结实验、题单、已生成补丁都没有覆盖。没有自动部署、调用付费模型或启动官方评测。实现目标是检验“早期试错中发现的局部障碍能否减少后期无效重试”，不是预先宣布优于 Raw，也不称为已学习因果规律或最小阻塞集。

## 执行闭环

1. 只从真实命令返回记录失败：精确动作、工作目录、错误摘要、来源快照、候选条件和证据状态。一条记录属于一个任务的一次尝试。
2. 失败先是 `hypothesis`，不立即禁止。模型再次提出同一个动作时，控制模式可以用一个固定模板的只读诊断替代本轮整个批次。
3. 诊断返回必须符合带随机标记的严格 JSON 格式，且与待检查动作、工作区/运行环境和当轮相符。超时、截断、非零、异常输出均为未知，不据此阻止执行。
4. 只有已支持的结构性必要条件确实缺失，才得到一次短期 `defer`。下一轮如果模型仍重复原操作，可以暂缓一次，反馈证据，让模型去修复前提、检查环境或换操作。
5. 修复导致相关状态变化、恢复快照、检查发现前提已满足、原操作实际成功，或模型说明理由覆盖，都能撤销阻塞。一次暂缓消耗后也允许真正重试，不形成永久黑名单。

例：`python missing_task.py` 失败，模型重复同一命令。系统检查该脚本是否存在；确实不存在时短暂暂缓重试。模型创建脚本后，下一次原命令正常执行。系统不会自行安装依赖、启动数据库、修改代码或执行模型提供的任意“诊断脚本”。

## 哪些可以控制，哪些只能提醒

- 明确缺失的工作目录、无法找到的可执行程序、Python 显式启动的缺失脚本，可通过限定诊断支持临时暂缓。
- 启动模块仅在原命令本来就采用 `python -I -S -m 顶层模块名` 这类限定隔离语义时允许诊断与控制。普通 `python -m ...` 保留为假设提醒，不用不等价的隔离环境检查替它下结论。
- 程序内部 `ModuleNotFoundError` 可以形成待检查假设，但不自动插入导入探针，不能推出“必须安装某个包”，也不能据此硬拦：代码可能调整 `sys.path`、切换解释器或使用回退路径。
- 断言失败、测试不通过、连接失败、权限错误、未知报错等默认只提醒。不把“连接失败”直接认定为“数据库没启动”，不让业务逻辑修复被错误环境假设取代。

## 匹配与失效

不是向量相似检索或关键词近似匹配。控制阶段精确匹配 `argv + cwd + stdin`，把种子和已知快照绝对路径归一到任务工作区；不同参数、目录或输入不会共用硬阻塞。前提检查绑定工作区指纹、目标状态、解释器/可执行程序及进程环境指纹。秘密环境值不写入记忆报告。

本版采用保守失效：工作区其他内容变化也可能使旧条件过期，从而允许重试。它宁可多执行一次，也不把不充分的依赖建模当作不变性证明。包安装、外部服务等状态无法完整冻结，因此额外用短期的一次性租约、每状态有限探针和显式覆盖防止死锁。

只检查批次中第一个未缓存的普通命令；没有普通命令时检查第一个验证命令。不会拿批次执行前的状态去禁止第二条命令，因为第一条可能正是在创建其前提。诊断或暂缓时，剩余整批命令都不执行，下一轮由模型重新决策，不偷偷删掉失败命令后继续运行后面的命令。

模型可以在命令决策中附加：

```json
{"retry_blocker": {"id": "已展示的阻塞记录ID", "reason": "为什么前提已变化或该假设不成立"}}
```

这是解除特定记录的可审计入口，不证明解释是真的，也不增加额外模型调用。畸形、未知 ID、空理由不能绕过检查。

最多保留 128 条记录；同条件重复观察聚合并保留最近证据，提示按确认状态和近期性选择完整条目，默认 4000 字符预算。不是把所有历史经验无界拼接到提示中。

## 预算与指标

每条记录同一状态最多 2 次探针、一次任务最多 8 次探针；探针始终占用原有工具上限和真实 CLI 反馈轮次。达到诊断上限后允许正常行动，不额外索要预算。一次暂缓占用决策轮数但没有工具调用。没有额外 LLM 经验提取、成功裁判或隐藏免费验证。

沿用原三项主指标：官方成功率、实际 CLI 反馈批次、同口径的工具调用冗余率。另记决策轮数、API 调用/token、耗时、探针数、暂缓数、释放/过期次数、记录展示次数。诊断阶段单独标记 `blocking_diagnostic`，仍进入总工具分母；比较时同时查看分阶段冗余数量与识别覆盖率，不能只看分母扩大后的比率。

`deferred_action_batches` 不是“已节省工具数”，也不是“正确拦截数”；没有反事实证据时，误拦率和因果节省数保持未知。诊断结果不进入任务功能验证成功台账，前提满足也不等于问题解决。自主提交和 Git 补丁交付沿用 v11 的共同逻辑。

结果含 `blocking_memory_mode`、`blocking_memory_metrics`、`blocking_memory_report`、`probe_tool_calls`、`deferred_action_batches`、`probe_budget_bypasses`。`evidence-trace.json` 保存原提议、实际诊断/暂缓、输出和快照来源；`search_checkpoint.json` 仍保存最近草稿。运行版本为 `blocking-cli-v12`。

## 先做三组小样本对照

`run_experience_ablation.py` 默认 `--study blocking`，接受已准备好的 1–10 题，统一模型、环境、命令批大小、决策/工具上限、官方评测方式；每题每组一次，不因失败换题或私自重试。

| 组别 | 失败条件记忆 | 自动探针/暂缓 | 原证据缓存/回退 |
| --- | --- | --- | --- |
| `raw` | 关闭，普通历史保留 | 无 | 关闭 |
| `blocker_advisory` | 展示同一种失败条件记录 | 无 | 关闭 |
| `blocker_control` | 展示失败条件与新增诊断证据 | 有 | 关闭 |

这能检验“提示式条件记忆”和“带检查的行动控制”整个方案的差异。两组获取的新证据不完全相同，因此不能单凭此三组把收益全归因于暂缓开关；若有收益，再加同探针但不暂缓的诊断对照。小样本只用于开发筛选，不能宣称统计显著。

```text
python run_experience_ablation.py --study blocking --task-manifest <已准备的小题单.json> --output-root <新的v12结果目录> --python <agent-python> --model deepseek-flash --dry-run
```

默认只生成计划，不创建实验结果、不调用模型。检查题目、模型、预算、协议哈希后再显式 `--execute`。API Key 仍仅从启动环境读取，不写入参数或报告。`--study evidence` 保留原四组消融，明确关闭阻塞记忆。

`run_comparison.py` 的完整方法为原任务证据/回退加控制模式，Raw 全关，适合测整体而非归因单个组件；协议明确冻结配置，不能混用历史 Raw。不要直接启动大实验。

## 验证边界

运行 `python validate_v12.py` 生成本版本离线回归收据 `VALIDATION_V12.json`。使用假模型与真实临时工作区/子进程，不使用付费 API；网络测试仅连接本地假服务。收据记录代码哈希、通过/跳过/失败、平台和时间。旧 v11 收据仅为历史，不能替代它。

2026-09-23 Windows 最终回归：632 项，621 通过、11 项平台/工具条件跳过，0 失败、0 错误；新增的 50 项阻塞记忆、执行控制和协议测试全部通过。跳过项涉及 Linux 进程/准备、符号链接权限、POSIX 执行位和缺少 `cat`；不能据此声称云端平台验证已完成。完整收据见 [VALIDATION_V12.json](VALIDATION_V12.json)，新增机制收据见 [VALIDATION_V12_FOCUSED.json](VALIDATION_V12_FOCUSED.json)。代码哈希与最终收据相符，旧 v11 代码哈希也仍与其原收据相符。

复制式执行工作区不是完整操作系统沙箱。诊断使用固定模板及验证副本，但任务 Python 的启动钩子/运行环境等仍须由外层容器隔离。Windows 离线通过不等于 Linux 云端验证，更不等于真实任务性能提升。
