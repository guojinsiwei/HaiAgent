# BestFGS v3：全局规划者 + 局部解题者

这是基于 `collaborative-graph-v2` 的独立候选版。核心决策拆成两个模型角色：**Planner 管全局路线与图上的假设，Solver 管当前现场的具体解题**。监控器与向导保留按需介入，默认总计四个角色客户端，不要求使用四种不同模型。

## 职责怎么分

| 组成 | 负责 | 不负责 |
| --- | --- | --- |
| 全局规划者 Planner | 读图、维护节点假设和路线状态、分配局部目标、选择扩展节点或已有候选边 | 不写/执行 shell，不虚构结果，不直接增删事实节点或修改预算 |
| 局部解题者 Solver（代码中仍叫 action） | 按局部目标读文件、写代码、诊断、提出具体候选动作和提交 | 不选择全图节点 ID，不自行切换快照 |
| 监控器 Monitor | 观察刚完成的分支、判断停滞、提取有证据的条件记忆 | 不把判断当作事实，不执行命令 |
| 向导 Advisor | 对具体卡点提出替代解释、检查建议和预期观察 | 不调度全图、不自动执行建议 |
| 程序 | 建立真实节点/边、保存恢复快照、验证规划选择、执行动作、核对证据、限制资源 | 不把规划模型的假设提升为事实 |

“建图、维护”分两层：真实执行形成**事实图**，程序维护其一致性；Planner 维护图上的**假设/路线解释层**。这层目前包含节点假设、open/parked/revisit 状态、证据引用，以及规划决定中的子目标和预期观察。模型不能凭空添加一个“测试通过”的节点。

## 主循环

1. 程序将刚执行的结果登记入图；按需交给监控器和向导。
2. 到规划时机，Planner 读取紧凑全局拓扑、当前可选节点/边、带节点归属的证据与条件记忆。
3. Planner 选择一个合法的 `expand N*` 或 `edge G*`，附局部目标和可观察的推进条件；可更新最多三个节点的假设标注。
4. 程序验证选择存在且当前可用，恢复其来源现场。规划说明绑定到恢复后的分支，不能污染切换前的分支。
5. 如果选择扩展节点，Solver 据此提出最多两个具体兄弟动作；如果选择已有边，程序执行其原有动作，Planner 不能偷偷换命令。
6. 执行反馈形成新节点或等价合并，记录规划来源与实际动作的关联，进入下一轮。

两个角色使用独立请求与上下文。Planner 看到全局紧凑信息；Solver 看到当前分支对话、证据、记忆和 `solver_assignment`。分支继承的目标会标为“需要依据当前证据重新检查”，不是不可质疑的高优先级指令。

## 何时调用规划者

- 初始任务：分配第一个局部目标。
- 出现尚未规划过的分叉：一个来源节点有多条待执行边。
- 观察到新的失败节点，或当前节点收到新的向导建议。
- 默认每 4 个恢复进度步进行一次进展规划检查。进度步继承现有工具调用与重复拦截计数，不是挂钟时间。

默认最多 **24 次规划尝试**，上下文预算 24,000 字符。所有规划模型调用计入同一 `max-turns`，错误调用也计费计数；剩余请求不足两次时不再调用规划者，为 Solver 保留至少一个请求。上下文构建失败同样消耗一次规划尝试，但不虚报模型调用。

没有触发、额度用尽或返回无效规划时，程序按原有启发式继续调度。不会循环请求“请重新规划直到合格”。因此本版是**事件驱动模型规划 + 程序持续调度**，不是每执行一条命令就额外调用一次 Planner。

## 规划输出与软状态

```json
{
  "selection": {"kind": "edge", "id": "G2"},
  "reason": "当前分支出现相同解析错误，另一候选检查配置来源",
  "subgoal": "确认实际加载的配置文件",
  "success_observation": "输出配置路径和关键字段，与任务要求比较",
  "node_updates": [{
    "node_id": "N1",
    "hypothesis": "当前解析错误可能来自配置来源错误",
    "status": "parked",
    "reason": "该节点的执行日志出现解析失败",
    "evidence_ids": ["E1"]
  }]
}
```

所有 ID 都必须在当次请求中提供。节点标注的证据必须属于该节点；跨分支引用被拒绝。坏标注不丢掉一个合法的调度选择。`parked` 只是 `-0.05` 的优先级调整，`revisit` 是 `+0.03`；都不封禁分支，数值尚未通过实测调优。

上下文最多提供 24 个详细可选项，同时给出全局紧凑拓扑；截掉的待选项会明确计数，仍保留在图里。Planner 不能选择未展示的 ID，这是控制上下文开销的限制，不代表看到了全图每条日志。

## 保留的工程机制

沿用 v2 的单题条件记忆、末尾记忆保护区、记忆更新后提案失效、规范化重复检测、恢复计数、ANSI 清洗、管道/检查状态区分、跨分支对话隔离、实际文件快照以及向导预测核对。没有重新引入三维正交硬门控。

记录 `proposed_under`（Solver 提案时的规划目标）与 `selected_by`（该边是否由 Planner 明确选中）。两者分别统计；程序自动选边不会假装经过模型规划。执行记录带来源/目标节点、证据 ID 和公开检查状态，但关联不等于规划带来了因果收益。

## 代码入口与产物

- `sources/bestfgs-project/src/bestfgs/graph_planner.py`：新增主文件，规划触发、图视图、输出校验、局部目标交接和规划审计。
- `graph_runtime.py`：程序事实图与执行循环；抽出只读待选集合构建和选中登记，供两个调度方式复用。
- `graph_collaboration.py`：既有监控、向导及执行后核对。
- `graph_roles.py`、`graph_cli.py`：独立角色配置及启动开关。
- `tests/test_graph_planner.py`：新角色分工专项测试。

新增 `audit/planner-state.json`：规划配置、调用数、决定、节点标注、提案关联和实际执行记录。原 `search-graph.json`、`collaboration.json`、完整请求/事件审计、记忆和结果文件均保留。`result.json` 新增 `planner_rounds`，`interaction_rounds` 包含四个角色。

## 本地验证与以后运行

```bash
python verify_graph.py
python run_graph.py --help
```

上述离线测试使用脚本化模型和临时文件夹具，不调用真实 API。本轮 Windows / Python 3.12 验证 **185 项通过，0 失败、0 错误、0 跳过**，其中新增规划者专项 19 项，覆盖真实文件恢复、角色隔离、共享预算、错误降级、两角色记忆读取及四角色协作。机器可读结果保存在 `offline-acceptance.json`。

真实执行仍要求 Linux 一次性隔离环境；待执行器验收后，可沿用 v2 的 `run_graph.py` 参数，并追加：

```bash
--graph-planner --planner-calls 24 --planner-interval 4
```

默认 Planner 与 Solver 使用同一模型、不同客户端。`--planner-model` 可指定另一模型；更换 provider/base-url 时必须同时显式提供模型名和 `--planner-api-key-env`，不隐式转发原端点密钥。

`--no-graph-planner` 关闭这次拆分，回到 v2 的协作图调度。保留统一的工程实现可用于后续对照。若只需 Planner/Solver 两个模型角色，可同时设置 `--advisor-calls 0 --no-semantic-monitor --no-auto-memory`；这也会关闭监控器的自动记忆提取，Solver 的记忆功能仍保留。
