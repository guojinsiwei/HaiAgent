一、HLD 语义规划
1. AppWorld 规划器只收到一套完整 JSON 协议，消除 routes/D ID 与 new_routes/N ID 两套说明并存。
2. 顶层 evidence_ids 漏写时，仅汇总模型已在方向和评估中明确引用的 ID。未知引用、显式错误类型仍被拒绝，不从已知 ID 列表伪造引用。
3. 周期评估允许继续已有有效方向，不强制为了凑格式编造新方向。初始规划和停滞重规划仍要求提出新方向。
4. 连续三条同一方向下、同一动作、同一完整输出且已知本地状态未改变的观察，可直接触发语义重规划，不再依赖 Monitor 报 stalled。新输出、不同方向、不完整回执、未知本地状态、通过的公开检查均有反例测试。
   这是一条保守的停滞线索；外部状态仍由 Planner 结合观察判断。它不会禁止普通命令，也不会证明任务失败。
5. 循环触发优先于周期检查，保留触发证据；Planner 选择其他可用语义方向后，下一次 Solver 请求收到更新方向。
6. Monitor 获得当前语义方向及明确的任务进展判断依据。HLD 指令移除旧的单动作正交探索、测量探针和八步探索回合要求。

HLD 的正确机制：识别循环/停滞 → 重新评估语义方向 → 选择后续多步方案 → Solver 执行 → 根据观察继续评估。
此前审计中“正交探索破循环”和用测量型实验次数评价 HLD 的口径撤回。

二、完成审查（HLD 与 KZDSH 共用修复）
1. 无效检查协议不会先写入永久任务缺口；格式问题保持为格式问题。
2. 新增 gap_refs，允许检查用本轮明确提出的缺口原文绑定控制器分配的 Gap ID。同一轮即可注册、执行、针对性关闭缺口。
3. 保留逐缺口证据、期望值来源和覆盖范围检查。全局 accept 无法关闭其他未验证问题；不存在的引用、伪造要求、失败或不完整回执仍无法通过。
4. 完成审查的进展统计纳入新执行观察和已关闭缺口。只读验证不再因为应用 revision 未变而统一算作无进展。重复编号的同一证据不会重置计数。
5. 只统计真实审查准入；连续无新证据的审查仍受限制，每个应用状态版本最多 8 次审查，防止无限换格式继续消耗。
6. 回执明确标识由控制器确认的命令身份；Critic 不再要求 Solver 重算控制器内部哈希。仍需判断公开要求与检查内容的实质覆盖。
7. 验证结束恢复此前只读状态，避免默认解除原有只读保护。
