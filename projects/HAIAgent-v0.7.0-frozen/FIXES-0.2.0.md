# 0.2.0：集成缺陷修复与原因

本次只修复新建的 HAIAgent，不修改冻结 BestFGS v14、不启动云端实验或付费调用。模型仍自主决定何时提交；成功率、平均交互轮次、语境工具调用冗余率的数学定义不变。

## 为什么此前测试通过，却仍有问题

不是“写了代码就理应没有 bug”，但这些边界本应在交付前验证。上次把组件单测、短示例和协议检查通过，过早表述为整体接入已完成，验证不足的责任在实现和交付过程。

最关键的遗漏是接口组合：组件测试通常给定明确版本，实际执行器却必须把通用命令后的环境版本设为未知；组件要求已知当前版本才能保存/召回经验，于是在真实接入时将经验路径关掉。两处单独看都保守，组合后却不符合组件用途。

同样，短历史不会触发预算剪裁，简单前台命令不会暴露后台服务问题；校验日志也不等于校验磁盘补丁。原 62 项测试覆盖了部分行为，没有覆盖所有真实场景。

## 已修改的内容

| 问题与证据 | 原因 | 修复 |
|---|---|---|
| 实际 Agent 连续两次报同样错误，后续提示中无经验 | 把“无法确认当前适用”误作“不能保留历史事实” | 自动重复失败/恢复可存为历史参考；当前有效与未知/过期明确区分，不虚构因果或禁止重试 |
| 长题面、大 stdin 与长输出时 Raw 下一轮丢失最新反馈 | 整对历史超过预算就直接跳过 | 两种模式都优先保留最新行动/反馈，显式压缩大文本，放不下则明确停止 |
| 子目录经验被拒、无关日志使代码记忆失效 | 当前 cwd 与来源 cwd 混淆，整仓指纹粒度太粗 | 保留来源目录；简单稳定文件读取的单来源代码发现按文件指纹校验；其它经验保守保留历史身份 |
| API 错误停止，CLI 却退出 0 | 只打印了结构化失败，没有传递调度退出码 | 区分提交、预算、API、基础设施与中断；0 不代表官方成功 |
| 修改提交文件后汇总仍接受；手填成功可与原报告相反 | 日志/报告摘要校验代替了实际产物/结果解释 | 核对实际补丁或终端提交记录；支持格式解析原始评测结果并对照 success；复制原报告以便移动运行目录 |
| 正常启动的后台服务可能因管道未关闭而被杀 | 将“读取线程仍活着”等同于失控进程 | 正常返回不杀组；超时仍清理；标记后台输出，外部容器在评测后销毁 |

另修复/强化：指纹扫描拒绝 FIFO 等特殊文件；消除对话反馈与组件近期记录的整份重复；协议记录源码哈希，配对汇总拒绝混用实现版本。

## 不是此次修复所能证明的事

- 没有证明新方法比 Raw 更强；也不能据此认定过去 BestFGS 的失败就是这些新工程问题导致。
- 文件依赖提取是保守的小范围支持，不是任意 Bash/Python 程序的语义依赖分析。
- 外部结果目前支持已有 SWE 报告结构；未实现完整 Harbor 生命周期/原始报告适配，未知格式拒绝导入。
- 原报告解析和哈希不能认证评测者或证明同一环境，仍需要可信外部 harness。
- Windows 离线验证不能替代 Linux 任务容器验证。尤其是进程树、FIFO 和评测后的环境清理仍需 Linux 集成检查。
- 语境冗余率仍需要带依据的离线审计，未审核不能报告为 0，更没有恢复机械重复率充当冗余率。

回归用例在 `tests/test_regressions.py`。它们测试反例及修复后的行为，不调用付费模型。
